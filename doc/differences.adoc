[#webrtc-differences]
== Differences from the W3C's API

webrtc follows the W3C's WebRTC API where a platform allows it. Where one
does not, the difference is here, with what a program gets instead.

What a target cannot honour follows one rule: by default it fails with
`operation_not_supported`; under the b2 feature
`webcpp-webrtc-unsupported=ignore` it is ignored, which a setting may be
only where the platform does something equivalent of its own. The feature is
propagated, so a whole program agrees, and setting both
`WEBCPP_WEBRTC_UNSUPPORTED_ERROR` and `WEBCPP_WEBRTC_UNSUPPORTED_IGNORE`
stops the build. Natively every setting is honoured, but a data channel's
`max_packet_life_time` of 0, which the rule decides
(<<webrtc-native-policy>>); in the browser the rule decides
`configuration::bind_address` (<<webrtc-browser-policy>>). A getter has no
failure to give: where a platform holds an attribute otherwise than the W3C
says, the table says what the getter returns, whatever the policy.

[cols="2,3",options="header"]
|===
| What | What a program gets

| `createOffer()`, `createAnswer()`
| Not offered. `async_set_local_description()` makes the offer or the answer
  and applies it, as the W3C's `setLocalDescription()` without an argument
  does; libdatachannel cannot apply a description made apart from it.

| `negotiationneeded`
| Not offered: only a connection's first data channel needs negotiation, and
  a program creates it before it offers; later channels open over the same
  connection without one. Natively automatic negotiation is off, so a
  description exists only when a program asks for one, on both targets.

| `configuration::bind_address`
| Not a W3C setting: natively, the one local address ICE binds to, which
  a program on the loopback needs. A browser cannot honour it: `make` fails
  with `operation_not_supported`, or ignores it under
  `webcpp-webrtc-unsupported=ignore`.

| a `stuns:` ICE server URL
| Natively not one: libdatachannel knows `stun:`, `turn:` and `turns:` alone,
  so `make` fails, the whole configuration with it, with `syntax_error`, as
  for a URL it cannot parse. In the browser a URL whose scheme the browser
  knows is its own to use: a browser that refuses one fails `make` with the
  error its constructor names.

| a local candidate's `sdp_m_line_index` and `username_fragment`
| Natively libdatachannel gives neither: webrtc sets `sdp_m_line_index` to
  0, the connection's one data section, and leaves `username_fragment`
  empty; the `sdp_mid` is enough for a peer, a browser included. In the
  browser a candidate carries all four members.

| a remote candidate's `username_fragment`
| Natively ignored, whatever the policy: libdatachannel makes one ICE
  session per connection and never restarts it, so every candidate belongs
  to it, and a candidate's own `ufrag` attribute, when its text has one,
  still reaches it. A browser peer's candidates carry the field, so refusing
  it would refuse them.

| a data channel's `max_packet_life_time` of 0
| Natively libdatachannel's C API takes an unreliable channel's limit as a
  lifetime when it is positive and as a number of retransmissions otherwise,
  and gives it back the same way, so a lifetime of 0 has no form of its own.
  By default `create_data_channel` fails with `operation_not_supported`; under
  `webcpp-webrtc-unsupported=ignore` it makes a channel of 0 retransmissions,
  announced to the peer as one, which both of its ends read as
  `max_retransmits()` 0 with an empty `max_packet_life_time()`. A channel the
  peer announced with a lifetime of 0 reads so too, whatever the policy. In
  the browser a lifetime of 0 stays one, at both ends.

| a text message holding a zero byte, or not UTF-8
| Natively a zero byte is not sent, `operation_not_supported` whatever the
  policy: the C API takes a text as a zero-terminated string, and cutting the
  message short silently is never what a program asked for. In the browser a
  zero byte is sent, and a text that is not valid UTF-8 fails with
  `type_error`, since the browser sends a JavaScript string.

| a received message past `options::max_message_size`
| A peer that keeps to the size announced in the description never sends
  one. Natively libdatachannel truncates one that comes anyway to that size,
  silently, since webrtc installs no logger for it, and webrtc delivers what
  it kept. In the browser the channel closes, and `async_receive` completes
  with `message_too_large`.

| unread messages
| Natively they wait in libdatachannel's queue of 1,024 messages a channel,
  which slows the peer down when it is full, and stalls the connection's
  other channels until the channel is read or closed
  (<<webrtc-channels-receiving>>). The browser has no flow control on
  receipt: past `options::max_received_bytes` the channel closes with
  `receive_overflow` (<<webrtc-browser-receiving>>).

| messages sent just before a channel is closed
| Natively they are delivered before the close. Chrome 156 may not deliver
  them at all when the sender closes the channel at once after sending them,
  as a page of plain JavaScript shows too; a sender that needs them read
  waits for the peer to say so before it closes.

| `runtime::peer_connections()` and the cap
| Natively the connections made with the runtime and not destroyed. In the
  browser the page's census, every connection of the page until it is
  garbage-collected (<<webrtc-browser-census>>).

| `RTCPeerConnection` and `RTCDataChannel` themselves
| No native handle, an `rtc` id or a browser object, appears in a public
  header: what a program needs is a member, and media, for which a handle
  was once kept, will get an interface of its own.
|===
