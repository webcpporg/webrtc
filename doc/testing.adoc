[#webrtc-testing]
== Testing

[#webrtc-testing-program]
=== Testing a program that uses webrtc

A test needs neither the network nor a second machine: two peers in one
process, each made with `configuration::bind_address` set to `"127.0.0.1"`
and no ICE server, connect through the loopback's host candidate alone, as
the examples of this page do. The test hands each peer's descriptions and
candidates to the other directly, in place of its signalling channel
(<<webrtc-signalling-trickle,trickling candidates>>), runs the `io_context` with a limit, so that
a broken exchange fails rather than hangs, and makes one `runtime` per case,
one case after another (<<webrtc-runtime>>).

[#webrtc-testing-library]
=== How webrtc is tested

webrtc's tests are under `test/`, each declared in `test/Jamfile`, and each
guarantee of <<webrtc-guarantees>> names the tests that hold it. They run on
two targets, {n-tests} tests in all, {n-tests-native} natively and
{n-tests-emscripten} on emscripten, under Node and in headless Chrome, with
every connection on the loopback and no STUN, so that a lane with no network
but the loopback runs them whole. The native suite runs as the build asks and
without exceptions:

[listing]
----
include::{library-root}/test/Jamfile[tag=native]
----

[cols="1,3",options="header"]
|===
| Test | What it checks

| the public headers
| Each compiled alone, with libdatachannel, as the build asks and, through
  the lint, without exceptions.

| `config`, `config_developer_defined`, `config_all_off`
| `<webcpp/webrtc/config.hpp>` defines `WEBCPP_WEBRTC_NO_EXCEPTIONS` exactly
  when webcpp has no exceptions, and keeps it when a developer defines it in
  a build that has them.

| `error`, `types`, and their `_no_exceptions` twins
| The category's name and fixed values, a message for each, the options'
  defaults, and the value types: their defaults, a description's and a
  candidate's view, and their text in a polymorphic allocator.

| `events`, `events_no_exceptions`
| The event machinery both implementations share, without a platform:
  states coalesce, one wait of a kind, a cancelled wait consumes nothing,
  the bound keeps a place for the end of gathering, a satisfied wait is
  posted, `close` aborts and then refuses, and an operation lives in its
  handler's allocator.

| `native`, `native_no_exceptions`
| Two peers on the loopback: a full exchange, messages received before the
  first read, a channel's attributes as created and as announced, a
  negotiated channel, errors as values, the bounds, `close`, a channel
  closed by its owner, destruction and moves, and `run()` returning once
  closed.

| `allocation`
| A connection pair over a polymorphic allocator on a counting resource:
  the state, a channel's protocol at both ends among it, the queues and the
  outputs allocate there, and nothing of it on another thread than the one
  that runs the `io_context`.

| `lifetime`
| Connections and channels destroyed while the peer floods them, repeated,
  and a channel flooded and never read destroyed in under two seconds.

| `stall`
| A channel past 1,024 unread messages stalls its connection's others, and
  its far end's destruction releases them.

| `bench`
| The receive benchmark's smoke pass (<<webrtc-native-cost,what reading a message costs>>): a few rounds
  of each path, each message checked.

| `browser_imports`, `browser_runtime`, `browser_backend`
| On emscripten, under Node, which has no `RTCPeerConnection`: the browser
  calls catch what JavaScript throws and report it by name, never
  re-entering {cpp}, and texts cross whole; the census and the cap, a slot
  freed once a connection is collected; and the browser implementation's
  semantics over a fake connection and channel of the test's own, a
  channel's attributes, the order of arrivals of different kinds,
  cancellation, a close with a notification in flight, and the `io_context`
  destroyed while handlers own the objects.
  Each runs with exceptions off too, and in the asyncify variant, its
  `_asyncify` twins, which form the own lane `asyncify` on emscripten, as
  webcpp::asio's do: a target that names `<webcpp-suspend>asyncify` belongs
  in a lane of emscripten's, since a build with no emscripten configured
  cannot expand that feature.

| `native_policy`, `native_policy_ignore`, and their `_no_exceptions` twins
| A data channel's `max_packet_life_time` of 0 under each policy: refused
  with `operation_not_supported`, or made with 0 retransmissions, which both
  of its ends read.

| `browser_policy`, `config_boundary`, `config_mismatch`
| `bind_address` under each policy, and two translation units with
  different policies that fail to link when they pass a channel between
  them, natively and on emscripten, with their twins likewise.

| the `browser` lane
| Two peers in one page of headless Chrome (`test/browser/`): every native
  case that applies and the browser's own, the receive budget and the size
  limit, refused sends, the close paths, allocation through a counting
  resource and `bind_address`, each program in both suspension variants and
  with exceptions off.

| the `interop` lane
| A native peer and a peer in headless Chrome (`test/interop/`), the same
  code against the public API, signalled through a relay over
  webcpp::beast's WebSocket on 127.0.0.1: each offers in turn, sends `ping`
  and gets `pong`, in both suspension variants; natively, two peers through
  the same relay.
|===

From the root of a webcpp checkout, the first two of these build and run
the tests and the examples natively, as the build asks and without
exceptions, and the third runs the tests under AddressSanitizer and
UndefinedBehaviorSanitizer:

[source,bash]
----
b2 threading=multi libs/webrtc/test libs/webrtc/example
b2 threading=multi exception-handling=off libs/webrtc/test libs/webrtc/example
b2 threading=multi address-sanitizer=norecover undefined-sanitizer=norecover libs/webrtc/test
----

On emscripten the tests run under Node, and the `browser` and `interop` lanes
in headless Chrome, which `CHROME` names, else Playwright's cached Chromium on
macOS. Both start Chrome with `--disable-features=WebRtcHideLocalIpsWithMdns`,
so that a page's host candidates are its addresses; the `browser` lane checks
first, with two peers of plain JavaScript, that the browser connects at all.
Chrome 156 offers a page with no media permission only its default-route
address, so the `interop` driver grants the page's origin the microphone,
which starts no capture, and the page then offers 127.0.0.1 too, where the
native peer listens. The lanes run by name:

[source,bash]
----
b2 toolset=emscripten webcpp-suspend=jspi libs/webrtc/test
b2 toolset=emscripten webcpp-suspend=asyncify libs/webrtc/test
b2 toolset=emscripten libs/webrtc/test/browser//browser
b2 threading=multi libs/webrtc/test/interop//interop
b2 toolset=emscripten libs/webrtc/test/interop//interop
----

The lifetime and native tests run under ThreadSanitizer too, the lifetime
test for 100 rounds, which checks webrtc's side of every hand-off between
libdatachannel's threads and the executor; libdatachannel's archives are not
instrumented:

[source,bash]
----
b2 threading=multi thread-sanitizer=on define=WEBCPP_TEST_WEBRTC_REPEAT=100 libs/webrtc/test//lifetime libs/webrtc/test//native
----

b2 compares timestamps, so a result that counts is built from scratch, with
`b2 -a`. The CI runs the tests on every native compiler of webcpp's lanes,
GCC, Clang on `libstdc++`, Apple Clang and MSVC, and on emscripten, the
`browser` lane with its pinned Chrome, and the test matrix of every run is at
https://webcpporg.github.io/report/.
