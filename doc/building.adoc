[#webrtc-building]
== Building a program

webrtc is header-only. A program inside a webcpp checkout names its target,
`/webcpp/webrtc//webrtc`, which brings the headers, webcpp::config,
webcpp::asio and, natively, libdatachannel:

[listing]
----
include::{library-root}/build.jam[tag=webrtc]
----

Natively that target is `/webcpp/third_party//libdatachannel`: libdatachannel
0.24.6 with libjuice, libsrtp, usrsctp and plog, built by the superproject
from the sources it pins, as static archives, with the program's compiler and
runtime settings, over the same source-built OpenSSL as webcpp::asio's TLS.
A first build makes them, and later builds reuse them. The submodule is
initialized once:

[source,bash]
----
git submodule update --init --recursive third_party/libs/libdatachannel
git submodule update --init third_party/libs/openssl
----

libdatachannel runs threads of its own, so a native program builds with
`threading=multi`; a request for `threading=single` stops the build, naming
the fix. webrtc works with exceptions on and off: natively it calls
libdatachannel through its C API, which catches every exception
libdatachannel throws and returns a code
(<<webrtc-native-exceptions,exceptions>>), so a program built with
`exception-handling=off` needs nothing more:

[source,bash]
----
b2 threading=multi libs/webrtc/example
b2 threading=multi exception-handling=off libs/webrtc/example
----

In the browser the same target brings webcpp::asio, whose usage requirements
link its browser runtime (the bridge's export and JavaScript, which
`<webcpp/asio/browser/src.hpp>` holds), embind and the flag of the suspension
variant `webcpp-suspend` chooses, `jspi` or `asyncify`: a program built with
b2 includes nothing more. A program built without b2 includes
`<webcpp/asio/browser/src.hpp>` in exactly one translation unit and links
with `-lembind`, `-sJSPI` (or `-sASYNCIFY` with JavaScript exceptions),
`-Wl,--export=emscripten_stack_get_current` and
`-Wl,--export=_emscripten_stack_restore`:

[source,bash]
----
b2 toolset=emscripten webcpp-suspend=jspi libs/webrtc/test
----

The convenience header `<webcpp/webrtc.hpp>` includes every public header.
`<webcpp/webrtc/config.hpp>` defines `WEBCPP_WEBRTC_NO_EXCEPTIONS` exactly
when webcpp has no exceptions, as every webcpp library's configuration does,
and stops with `#error` on WASI, where no WebRTC exists.

The b2 feature `webcpp-webrtc-unsupported=error|ignore`, propagated, chooses
what a setting a target cannot honour does: fail with
`operation_not_supported`, the default, or be ignored where the platform does
something equivalent of its own (<<webrtc-differences>>). Natively it
decides a data channel's `max_packet_life_time` of 0
(<<webrtc-native-policy>>), in the browser `configuration::bind_address`
(<<webrtc-browser-policy>>). On both targets the classes live in an inline
namespace named after the policy, `unsupported_error` or
`unsupported_ignore`, so their spelled names are the same,
`webcpp::webrtc::peer_connection` among them, and two translation units
built with different policies that pass an object between them fail to link
instead of disagreeing at run time.
